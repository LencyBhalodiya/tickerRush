01

System overview

Who talks to whom, and where the data lives.

Key points

  • The browser calls the API directly, cross-origin. The Next.js server is not in the request path.
  • CORS lets exactly one origin in (CORS_ORIGIN), with credentials, so the refresh cookie can travel.
  • Only the API touches MongoDB. Dev data is in ticker-rush-dev; npm test uses ticker-rush-test.
  • Dev ports: front-end 5173, API 8080 (PORT, default 3000).
  • Requests never send email. They add a job to Redis, and the worker sends it, with retries (section 07, continued).

Rules

  • Dependencies point one way: routes → controller → service → model.
  • Controllers own HTTP. Services never see req or res.
  • Services fail by throwing AppError. No try/catch in controllers: Express 5 forwards rejected promises.

04

Auth router

How every /api/v1/auth route is guarded (auth.routes.ts).

Key points

  • The auth limiter counts every request under /auth, including invalid bodies and unknown paths.
  • validateBody parses with zod and replaces req.body with the clean value: trimmed, email lowercased, unknown keys dropped.
  • The sign-in limiters run after validation, so A@x.com and a@x.com share one counter.
  • cookieParser is mounted on this router only: the refresh_token cookie is scoped to /api/v1/auth, so no other route receives it.
  • Any step can fail into errorHandler: 429 from a limiter, 422 from validation, 400, 401 or 403 from the service.

Rate limits

Four limiters: three stop password guessing, one stops inbox flooding.

LimiterApplies toCounted perLimitWhat countsStops

How they're implemented

express-rate-limit with fixed 15-minute windows; responses carry the IETF RateLimit and RateLimit-Policy headers. Counters live in process memory: they reset on restart and are not shared between instances. trade-off The email-only limiter lets anyone lock an email out of sign-in for up to 15 minutes.

07

Sign-up flow

POST /api/v1/auth/signup, step by step.

Key points

  • The email is trimmed and lowercased first, so Ada@X.com and ada@x.com are one account.
  • zod drops unknown keys: sending "role": "admin" does nothing.
  • Passwords are hashed with argon2id at the OWASP minimum cost.
  • No exists pre-check: the unique email index decides, which also covers two sign-ups racing.
  • A taken email gets the same 202 after the same work: one hash, one insert, one job added to Redis. The link is made after the reply, by the worker.
  • A taken email warns the owner but never gets a verification link (it would verify whoever registered first). No email includes the name.
07

Email queue

How every email leaves: a job in Redis, sent by a BullMQ worker (auth.emails.ts).

Key points

  • A job holds only {kind, email}, never a link: a token in Redis would undo storing only its hash.
  • The worker does the account lookup, so resend and forgot-password do the same work (one add) for any email.
  • Sending fails → the job is retried after 30 s, 1, 2, 4 and 8 minutes, about 15 minutes in all.
  • Redis down → add() gives up after about 2 s and the request gets 503 EMAIL_UNAVAILABLE, never a hang.
  • Shutdown waits for the emails being sent. A crash mid-send is retried after the job's lock expires (about 30 s), so an email can arrive twice; only the newer link works.
  • Tests use the test: key prefix, so the npm run dev worker never takes their jobs.
08

Sign-in flow

POST /api/v1/auth/signin, step by step.

Key points

  • Unknown email and wrong password get the same 401 body, and the dummy hash makes them take the same time.
  • 403 for an unconfirmed email comes only after the password matches, so it reveals nothing.
  • The access token goes in the body. The refresh token goes only in the cookie.
  • Only a sha256 of the refresh token is stored, with user-agent and IP for a future "your devices" list.
  • JWT exp, database expiresAt and cookie Expires come from one Date.
  • Logged as signin_failed {reason} or signin_succeeded {userId}, never with the email.
09

Refresh and logout

POST /api/v1/auth/refresh and /logout: both read only the refresh_token cookie.

Refresh

  • Rotation: every refresh revokes the old token and issues a new one. The atomic update means two requests with one token can't both claim it.
  • Reuse detection: only rotation sets revokedAt, so a revoked token coming back means someone kept a copy. Logged as refresh_token_reused.
  • 10-second grace: covers two tabs loading at once, like Okta's grace period and Auth0's reuse interval.
  • Session cap: ends after 7 idle days, or 30 days after sign-in at most.

Logout

  • Deletes this device's record (not revoke, so it never looks like reuse), clears the cookie with the same options, always 204.
  • No access token needed: it may already have expired.

Data model

Two collections: accounts, and the tokens issued to them.

Indexes and why

  • authaccounts.email unique: one account per email; catches sign-up races.
  • authtokens.tokenHash unique: finds a presented token in one lookup.
  • authtokens {userId, type}: reuse detection deletes every refresh token of one user; also serves userId-only queries.
  • authtokens.expiresAt TTL: MongoDB deletes expired tokens itself (about once a minute).
  • select: false hides passwordHash and tokenHash unless a query asks for them.
13

Startup and shutdown

How the process comes up, and how it goes down cleanly (server.ts).

Key points

  • MongoDB and Redis connect before the port opens, so the API never takes traffic it can't serve. BullMQ would wait for Redis forever, so startup gives up after 10 s.
  • A bad or missing env variable stops the process at import time with a zod error.
  • On SIGINT/SIGTERM the server stops accepting, lets in-flight requests finish, lets the worker finish the emails it is sending, then closes Redis and MongoDB. Queued jobs wait in Redis for the next start.
  • Crashes take the same path and exit with code 1.

Security controls

Each threat, what stops it, and where that lives in the code.

ThreatControlWhere
Stolen databasePasswords: argon2id, 19 MiB, 2 passes, 1 thread (OWASP minimum), not selected by default. Refresh and link tokens: only sha256 hashes.auth.service.ts, auth.tokens.ts
Someone registered your email firstThey can't sign in until it's confirmed, and links only go to the inbox. A reset sets your password, confirms the email and deletes every refresh token.auth.service.ts · resetPassword
Password guessingThree layered rate limits (section 06).auth.routes.ts
Email enumerationSign-in: identical 401, plus a dummy argon2 verify so timing matches. Sign-up, resend, forgot: identical 202 after the same work, no pre-check.auth.service.ts, auth.emails.ts
Stolen refresh tokenRotated on every use. A rotated token coming back (after a 10-second grace) deletes every refresh token of that user. Sessions end 30 days after sign-in regardless.auth.service.ts · refresh
Tokens leaking: XSS, cachesRefresh token is HttpOnly. Access token lives only in memory and expires in 15 minutes. Cache-Control: no-store on token responses.auth.controller.ts, front-end session.tsx
CSRF and login CSRFSameSite=Strict cookie scoped to /api/v1/auth. JSON-only bodies force a CORS preflight that only CORS_ORIGIN passes.app.ts, auth.controller.ts
Forged or confused JWTsHS256 pinned on verify, a separate secret per token kind, kind and role checked.auth.tokens.ts
Phishing via our emailsPlain text, and the user's name is never included.auth.service.ts · signUp
Privilege escalation, NoSQL injectionzod drops unknown keys, so role can't be set at sign-up, and requires strings, so objects like {"$gt": ""} get 422.auth.validation.ts
Oversized input, CPU abuse1 MB body limit, max lengths on every field, password capped at 128 characters before hashing.app.ts, auth.validation.ts
Secrets in logspino redacts password and token fields; request logs keep only method and URL; auth events log userId, never email.config/logger.ts
Clickjacking, MIME sniffinghelmet default headers.app.ts
MisconfigurationEnv validated at startup; bad values crash immediately.config/env.ts

Testing · npm test

  • Node's built-in node:test over src/**/*.test.ts. NODE_ENV=test turns logs off and makes the mailer's jsonTransport send nothing.
  • Starts the real app on a random port and calls it with fetch; no supertest.
  • Same MONGODB_URI, but dbName is overridden to ticker-rush-test; Redis jobs use the test: prefix.

Covered today

  • Sign-in: token, cookie flags, hash-only storage, identical 401s, 429 on the 6th failure.
  • Sign-up: a taken email looks identical to a new one.
  • Email links: each works once; resend and forgot reply the same to any email; a reset ends every session.
  • Refresh: rotation, grace window, reuse ends every session, 30-day cap.
  • Logout: 204 with or without a cookie; the token stops working.

Known gaps and next steps

What isn't safe or finished yet, and the plan for each.

GapRisk todayPlan
JWT secrets only need 15 charsA short HS256 secret can be brute-forced offline from any token.Raise the zod minimum to 32, as .env.example already says.
Rate limits in memoryFine for one process; each extra instance multiplies the real limit.Move to a Redis store when running more than one instance.
trust proxy not setBehind Nginx or a load balancer every client shares the proxy's IP, so one user can rate-limit everyone.Set it to the proxy hop count at deploy time.
Sign-up can email any addressNo per-email limit, only the auth limiter (20 per IP per 15 min).Per-email limit, like resend.
Sign-up writes MongoDB, then Redis trade-offIf Redis fails, sign-up deletes the new account and replies 503, so a retry starts over. A crash between the two leaves an account without an email.Accepted: "Email me a new link" on sign-in recovers. A transactional outbox if it matters.
Worker in the API process trade-offSending shares the API's CPU and restarts with it.Start startEmailWorker() from its own entry file when email volume grows.
Access token after logout trade-offStays valid for up to 15 minutes after logout, reuse detection or a password reset.Keep it short-lived. Add a jti denylist only if a route needs instant revocation.
Lost refresh response trade-offIf the new cookie never arrives and the browser retries after the 10-second grace, reuse detection signs the user out everywhere.Accepted: safer than letting an old token work indefinitely.
Refresh shares the auth limiter trade-offEvery full page load spends 1 of the 20 requests per 15 minutes.Give /refresh its own, higher limit if users hit 429.
Per-email lockout trade-offAn attacker can block a user's sign-in for up to 15 minutes.Accepted for now; revisit with CAPTCHA or progressive delays.
